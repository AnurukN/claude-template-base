# Add general-purpose frontend/backend/tester/teamlead agents outside the DS/MLE persona scope

This template's agents so far (`data-scientist`, `ml-engineer`, `model-evaluator`, `cost-estimator`) all serve the DS/MLE ML pipeline scoped in `0002-phase-1-persona-scope.md`. We added a `frontend-developer` agent anyway, at the user's request, for a separate team building a web app (e.g. a dashboard or standalone app) unrelated to the ML pipeline, that wants to reuse this repo's Claude Code setup rather than stand up its own. We chose to add it as a plain, framework-agnostic agent with no ML-specific context — rather than folding ML awareness into it or refusing it as out of scope — because that team's work has nothing to do with SageMaker training, evaluation, or deployment: it needs neither the SageMaker submission guardrail nor any DS/MLE agent's domain knowledge, and adding it alongside the ML-specific agents costs the ML personas' workflow nothing. This doesn't reopen the Phase 1 scope decision in ADR 0002 — that decision still governs which *ML-specific skills* this template ships; it only establishes that an unscoped general engineering agent can coexist here for other teams sharing the repo, the same reasoning already applied to the general skills bundle in `0004-keep-general-engineering-skills-bundle.md`.

We later added `backend-developer` under the same reasoning, for the server side of that same team's web app — it's the natural counterpart to `frontend-developer` on the same non-ML codebase, so the same "unscoped, ML-agnostic, costs the DS/MLE workflow nothing" logic applies without a separate decision to make. We added `tester` under the same reasoning again, for automated tests across that same non-ML codebase — it's explicitly scoped to application-code testing, not model quality, so it doesn't overlap with `model-evaluator`'s job of judging metrics. We added `teamlead` last, as a read-only coordinator over the other three (task breakdown, cross-cutting consistency between frontend and backend, merge-readiness verdicts) — it never implements anything itself, which keeps the division of labor real instead of one agent quietly doing the whole team's job.
