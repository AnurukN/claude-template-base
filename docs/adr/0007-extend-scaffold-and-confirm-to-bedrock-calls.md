# Extend scaffold-and-confirm's hard enforcement to Bedrock/Anthropic calls

[ADR 0001](/docs/adr/0001-scaffold-and-confirm-execution-model.md) established that Claude never submits a billable SageMaker job/endpoint itself, enforced deterministically by `block_aws_submit.py` rather than left as a convention Claude is trusted to follow. `/label-data`'s Hybrid mode introduces a new billable action outside that hook's scope: a batch script that calls a vision-capable Claude model via Bedrock or the Anthropic API once per item, which racks up real, uncapped, per-call cost over a large dataset the same way a SageMaker job racks up per-instance-hour cost.

We chose to extend the hard-enforcement pattern rather than rely on `/label-data` simply asking nicely for confirmation in its own instructions. A soft convention is exactly what ADR 0001 already rejected for SageMaker jobs, for the same underlying reason: Claude shouldn't be trusted to self-police a billable action just because the specific API it's calling wasn't the one the original guardrail was written for. A new sibling hook, `block_bedrock_submit.py`, denies Bash commands that would invoke `invoke_model`/`invoke-model` or the Anthropic SDK's `.messages.create(...)` directly, the same way `block_aws_submit.py` denies SageMaker submit commands — `/label-data` generates the script and a cost estimate, and the human runs it themselves.
